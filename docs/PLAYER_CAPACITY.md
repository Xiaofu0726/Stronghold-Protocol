# 20 人房间扩展

本分支 `feat/20-player-rooms` 基于 `sganggs/Stronghold-Protocol` 的 `master`，基线提交为
`c9d804f470b8d7422ae04eb66faf671cef21ad52`。扩容实现参考 LongQianChen 的
`feat/IncreasePlayerCapacity`，不合入该分支的其他功能。

## 房间与卡池

合作房间默认 4 人，房主在开局前可选 4、8、10、16、20 个座位；缩容不得移除有人占用的座位。
实际参赛人数可以少于容量。单人模式不变。1–4 人继续使用上游选卡流程和随机序列。

扩容房间在开局时按座位顺序固定分组。组内共享干员和装备库存，跨组互不扣库存；离场后不重新分组。
5 人组库存为上游合作池的 1.25 倍，三阶干员向下取整，其余向上取整；3、4 人组保留完整合作池。
玩家的自选干员仍是上游的独立库存，不再按组人数放大。装备库存负债也分别归属各组。

| 实际人数 | 各组人数 |
| --- | --- |
| 1–5 | 单组 |
| 6 / 7 / 8 / 9 | 3+3 / 4+3 / 4+4 / 4+5 |
| 10 / 11 / 12 / 13 | 4+3+3 / 4+4+3 / 4+4+4 / 5+4+4 |
| 14 / 15 / 16 / 17 | 4+4+3+3 / 4+4+4+3 / 4+4+4+4 / 5+4+4+4 |
| 18 / 19 / 20 | 4+4+4+3+3 / 4+4+4+4+3 / 4+4+4+4+4 |

## 扩容所需的对局适配

- 策略和机变按固定组并行选取，各组独立计时。机变每组仍为 6 张，整场事件类型相同，各组分别抽牌。
  策略重复检查限于组内。保留上游的“AI 队友最后选择”选项，默认关闭。
- 联防次数上限按开局组数确定，最多 5 次，每次仍使用上游的双人援助战场；离场不会降低既定次数。
- 领袖共享血量按实际存活人数计算，人数上限由 4 放宽至 20；超过 4 人时，隐藏核心所需层数按
  `ceil(上游门槛 × 存活人数 / 4)` 扩展。战斗引擎、技能、敌人和数据表沿用上游。
- 协议和页面支持 20 个座位、分组选卡、团队面板、战斗统计与联防来源。大房间的战果若超出原协议
  安全上限，客户端交还服务端复算，避免截断漏怪导致少扣生命；小房间保留上游战果处理。

这些分组、库存和阈值是扩容分支的自定义规则，不是官方玩法规定。

## 与上游保持一致的部分

缓存与素材导入、HTTP/网络层、依赖、战斗模拟与技能、游戏数据、单人断线时限、AI 托管、插件能力
保持上游方案。没有引入多人参考分支的额外聊天、公告、房间发现、房主转移、服务器设置或缓存服务。

后续同步使用每小时自动镜像和受验证保护的 Git 合并，见 [两分支上游同步](UPSTREAM_SYNC.md)。扩容适配集中在
`shared/playerCapacity.js`、`server/match/match/capacity*.js`、`server/match/capacity/`、
`public/js/ui/capacity/` 和 `public/css/player-capacity.css`。
新增并发选卡方法只在开局人数超过 4 人时启用；原有小房间方法保留，便于逐次对照上游。

### 扩展代码的放置与合并边界

优先新增独立模块，在上游文件中保留必要的导入、调用和容量参数。当前划分如下：

| 扩展 | 独立文件 | 上游接入点 |
| --- | --- | --- |
| 席位上拉菜单 | `public/js/ui/capacity/roomCapacity.js` | `screens/lobby.js` 管理容量状态并传给 `room.create` |
| 分组机变页面 | `public/js/ui/capacity/choiceOverlay.js` | `ui/choiceOverlay.js` 保留上游小房间组件；把现有卡牌工具传给扩容组件 |
| 扩容布局与关闭按钮修正 | `public/css/player-capacity.css` | `public/index.html` 增加一个样式引用；六个原页面样式文件与 master 一致 |
| 大房间方法分派 | `server/match/capacity/install.js` | `Match.js` 在上游方法安装完毕后调用一次 |
| 固定卡池分组 | `server/match/capacity/pools.js` | `Match.js` 与 `match/setupVote.js` 创建或重建卡池 |
| 连续联防 | `server/match/capacity/unite.js` | `unite.js` 继续共用上游漏怪、悬赏与归因逻辑，仅在大房间扩展计划和援助顺序 |
| 分组与计时校验 | `server/match/capacity/audit.js` | `audit.js` 调用独立校验器 |

这些是仓库内的普通模块，不需要安装玩法插件。原有协议校验、房间人数、交易选池、领袖人数缩放、
分组数据转换、战斗报告和页面接线仍需要修改上游文件；不能仅靠新增文件完成扩容。

合入上游时，应先保留其最新实现，再检查上述接入点。独立模块减少同一文件内的文本冲突，
但上游接口或玩法语义改变时，仍须检查扩展模块是否需要跟进，尤其是分组机变页面的渲染。
不要通过整段复制上游模块、屏蔽冲突或修改镜像 master 来避免合并检查。

## 验证

扩容用例覆盖 1–20 人分组、独立库存、20 个真实 WebSocket 客户端、并行选卡、联防、协议和页面数据模型。
运行 `node tools/ci.mjs --keep-going` 和 `node tools/golden.mjs`；黄金基准不因扩容而改写。
浏览器中的 20 人长时间运行及性能仍需在实际部署环境中测试。

### 四人兼容边界

开局参赛人数不超过 4 时，策略、机变、联防及结算走上游原方法。多轮联防和结算事件中的
`uniteResults` 仅用于大房间；四人机变保持上游双击确认组件，团队面板保持上游的直接行结构。
差分检查工具使用同一份上游测试驱动，比较完整对局消息、结算事件、随机流状态、库存和最终结果：

```sh
node tools/check-four-player-parity.mjs --upstream /path/to/clean-upstream-checkout
```

上游对照目录须已安装依赖并运行 `node tools/vendor.mjs`。工具不修改两个仓库的源码。
这是游戏行为兼容性检查，不要求四人房的大厅/房间容量控件、人数说明或新增协议字段与上游相同。
全局协议允许 0–19 座，因此手写非法席位请求的校验错误也可能与原先的 0–3 座协议不同。

另有默认关闭的插件模式扩展：[固定盟约配置](MODE_BANDS.md)。它只有在所选模式显式配置时才启用，
普通四人/二十人房间的选盟约流程保持原样。
